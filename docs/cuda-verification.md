# Подтверждение наличия CUDA

`scripts/verify-cuda.sh` встроен в каждый образ как команда `verify-cuda` и
запускается в CI после каждой сборки. Проверка идёт тремя уровнями.

## Уровень 1 — статический

Отвечает на вопрос: пригоден ли образ для сборки CUDA-кода.

* `nvcc` присутствует и сообщает версию;
* `libcudart` найдена в образе;
* наличие или обоснованное отсутствие `libcuda.so`.

Про `libcuda.so`: в Jetson-образах её нет и быть не должно — это драйверная
библиотека, которую подмонтирует `nvidia-container-runtime` на устройстве.
Скрипт отмечает это как пропуск, а не как ошибку. Без такого различения все
Jetson-сборки были бы ложно красными.

## Уровень 2 — компиляционный

Отвечает на главный вопрос: действительно ли CUDA была применена при сборке,
а не просто лежит в образе.

Проверяется на пакете `cuda_probe` — это ROS2-нода из `src/cuda_probe`,
содержащая настоящее CUDA-ядро:

* бинарь `cuda_probe_node` слинкован с `libcudart`;
* `cuobjdump` находит в бинаре скомпилированный GPU-код;
* среди найденных архитектур присутствует целевая (`sm_87` для Orin).

Последний пункт — самое ценное. Он ловит характерную ошибку кросс-сборки:
если `CMAKE_CUDA_ARCHITECTURES` не передать явно, CMake подставит архитектуру
сборочной машины. Сборка пройдёт успешно, образ будет выглядеть исправным, а
на Jetson не запустится ни одно ядро. Здесь это видно сразу.

Уровень не требует GPU и потому выполняется в том числе для arm64-образов,
собранных на x86-раннере.

### Почему нужен отдельный пакет

FAST-LIO2 и FAST-LIVO2 в апстриме CUDA не используют: это CPU-код на Eigen и
PCL. Требование ТЗ «собираемые библиотеки должны иметь поддержку CUDA» для них
означает, что CUDA доступна пакету — `nvcc` в PATH, `find_package(CUDAToolkit)`
работает, флаги переданы. Но подтвердить фактическую кросс-компиляцию CUDA на
таком пакете невозможно: компилировать нечего.

`cuda_probe` закрывает этот пробел. Он же служит smoke-тестом самих базовых
образов.

## Уровень 3 — runtime

Выполняется только там, где есть GPU: на self-hosted раннере или при ручном
запуске образа на устройстве.

* `nvidia-smi` видит устройство;
* `cuda_probe_node --selftest` выполняет ядро на GPU и проверяет результат
  поэлементно.

При отсутствии GPU уровень помечается как пропущенный. Это ожидаемое
состояние для всех кросс-сборок в CI.

## Запуск вручную

```bash
# в собранном образе
docker run --rm ghcr.io/<owner>/<repo>/cuda-probe-x86-gpu:latest verify-cuda

# на устройстве, с доступом к GPU
docker run --rm --runtime nvidia \
  ghcr.io/<owner>/<repo>/cuda-probe-jetson-agx-jp6:latest verify-cuda
```

## Как читать вывод

```
  ✓  проверка пройдена
  ✗  проверка провалена — код возврата будет ненулевым
  —  проверка пропущена: условия для неё отсутствуют (нет GPU, нет бинаря)
```

Пропуски на уровне 3 при кросс-сборке — норма. Пропуски на уровне 2 означают,
что образ собран не из `cuda_probe`; для образов других пакетов это ожидаемо.
Любой значок `✗` — реальная проблема.
