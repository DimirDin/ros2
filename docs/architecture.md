# Архитектура системы

## Что решается

Один ROS2-пакет нужно собрать в Docker-образ под три разные платформы, каждая
со своей версией CUDA, своим дистрибутивом ROS и своей архитектурой процессора.
Наивное решение — три отдельных Dockerfile на пакет — не масштабируется:
добавление четвёртого пакета означает три новых файла и три правки в CI.

Система разделена на три слоя, каждый со своей частотой изменений.

| Слой | Что описывает | Как часто меняется |
|---|---|---|
| `platforms.yaml` | целевые платформы | редко |
| `base/*.Dockerfile` | ОС, ROS2, CUDA | редко |
| `packages/*.yaml` | конкретный ROS2-пакет | при каждом новом пакете |
| `templates/package.Dockerfile` | как вообще собирается любой пакет | почти никогда |

Добавление пакета затрагивает только третий слой — один YAML-файл.

## Различия платформ

| | x86-gpu | jetson-agx-jp6 | jetson-nano-jp7 |
|---|---|---|---|
| Процессор | x86_64 | ARM64 (Cortex-A78AE) | ARM64 (Cortex-A78AE) |
| GPU | дискретная NVIDIA | интегрированная Orin | интегрированная Orin |
| Compute capability | 7.5 / 8.6 / 8.9 | 8.7 | 8.7 |
| JetPack | — | 6.2.2 | 7.2 |
| Jetson Linux (L4T) | — | r36.5 | r39.2 |
| Ubuntu | 22.04 | 22.04 | 24.04 |
| ROS2 | Humble | Humble | Jazzy |
| CUDA | 12.6 | 12.6 | 13.2 |
| Память | раздельная CPU/GPU | единая | единая |

AGX Orin и Orin Nano имеют одинаковый GPU-архитектурно (compute capability 8.7)
и различаются числом SM, объёмом памяти и энергопакетом. Для сборки это значит,
что `CMAKE_CUDA_ARCHITECTURES=87` одинаков для обеих плат: разными их делает
версия JetPack, а не код GPU.

## Почему на JetPack 7 не Humble

ROS2 Humble — это релиз под Ubuntu 22.04, и бинарные пакеты в
`packages.ros.org` собраны только под неё. JetPack 7 построен на Ubuntu 24.04,
для которой доступен Jazzy.

Варианты были такие:

1. Собрать Humble из исходников на 24.04. Это несколько часов сборки на каждый
   образ и постоянные конфликты версий Boost, TBB и OpenCV между тем, что ждёт
   Humble, и тем, что есть в Noble. Хрупко и дорого.
2. Оставить Orin Nano на JetPack 6. Тогда обе Jetson-платформы отличались бы
   только числами в `CUDA_ARCH`, и задача кросс-платформенности выродилась бы.
3. Использовать Jazzy на JP7.

Выбран третий. Шаблон сборки читает `ROS_DISTRO` из базового образа и нигде не
предполагает конкретный дистрибутив, поэтому манифест пакета от этого выбора
не зависит — тот же `packages/fast-lio2.yaml` собирается и под Humble, и под
Jazzy.

## Почему базовые Jetson-образы собираются с нуля

Официальный `nvcr.io/nvidia/l4t-jetpack` опубликован только до тега `r36.4.0`
(ноябрь 2024). Ни под L4T r36.5 (JetPack 6.2.2), ни под r39.2 (JetPack 7.2)
готовых образов в NGC нет.

Поэтому базы собираются из чистой Ubuntu плюс официальные apt-репозитории
NVIDIA — те же источники, из которых NVIDIA собирает свои образы:

```
https://repo.download.nvidia.com/jetson/common/  r36.5   →  CUDA 12.6
https://repo.download.nvidia.com/jetson/t234/    r36.5
https://repo.download.nvidia.com/jetson/common/  r39.2   →  CUDA 13.2
https://repo.download.nvidia.com/jetson/som/     r39.2
```

Обратите внимание: в r39.2 разбивка по SoC (`t234`) заменена общим
репозиторием `som`. Поддержка Orin в JetPack 7 подтверждается наличием там
пакета `cuda-compat-orin-13-2`.

Побочная польза: версия L4T пинуется явно и воспроизводимо, а не наследуется
из тега чужого образа.

### Чего в Jetson-образах намеренно нет

Пакеты `nvidia-l4t-*` не устанавливаются. Их postinst-скрипты рассчитаны на
реальный rootfs Tegra и в контейнере не отрабатывают. Для компиляции они и не
нужны: достаточно CUDA Toolkit. Библиотеки времени выполнения — `libcuda.so`,
драйвер, Tegra-специфичные библиотеки — подмонтирует
`nvidia-container-runtime` при запуске на устройстве.

Практическое следствие: `ldd` на сборочной машине покажет ненайденные
CUDA-библиотеки, и это нормально. `scripts/verify-cuda.sh` различает
«отсутствует в образе» и «ожидается от рантайма», иначе проверки были бы
ложно красными.

## Способы сборки

| Способ | Где выполняется | Эмуляция | GPU |
|---|---|---|---|
| `native` (x86) | `ubuntu-22.04` | нет | нет |
| `cross` | `ubuntu-22.04` + QEMU | да | нет |
| `native-arm` | `ubuntu-24.04-arm` | нет | нет |
| `native` (Jetson) | self-hosted Jetson | нет | да |

`cross` — кросс-платформенная сборка через `docker buildx` и `binfmt_misc`.
Каждая инструкция ARM64 транслируется QEMU, поэтому компиляция C++ идёт в разы
медленнее нативной; для тяжёлых зависимостей вроде PCL это десятки минут.
Кеширование слоёв здесь не оптимизация, а необходимость.

`native-arm` использует бесплатные ARM64-раннеры GitHub: настоящая нативная
компиляция без эмуляции, но без GPU. Это делает нативную ARM-сборку доступной
без физического Jetson.

`native` на Jetson добавляет единственное, чего не дают остальные, —
выполнение CUDA-ядер на реальном GPU. Job описан в матрице, но по умолчанию
исключается: `runs-on` на незарегистрированный self-hosted раннер не
пропускается, а бесконечно висит в очереди. Включается флагом
`include_self_hosted` при ручном запуске.

### Почему не официальный кросс-компилятор NVIDIA

NVIDIA поставляет пакеты `cuda-cross-aarch64`, позволяющие компилировать
CUDA-код под ARM64 прямо на x86 без эмуляции — заметно быстрее QEMU. Путь
рассмотрен и отвергнут: он рассчитан на самостоятельные CMake-проекты с явным
toolchain-файлом, тогда как `colcon` и `rosdep` требуют полноценного целевого
rootfs со всеми ROS2-пакетами под ARM64. Собирать такой sysroot пришлось бы
всё равно через эмуляцию, что сводит выигрыш на нет.

## Публикация и теги

Один образ собирается несколькими способами, дающими функционально
идентичный результат. Если бы публиковали все, они наперегонки перезаписывали
бы один тег. Поэтому канонический тег пишет только первый способ из
`build_methods` (`native` для x86, `cross` для Jetson), остальные публикуются
с суффиксом способа: `...-native-arm`. Это позволяет сравнить результаты
разных способов сборки, не создавая гонки.
